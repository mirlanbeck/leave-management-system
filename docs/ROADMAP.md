Состояние: 2026-10-23 (время сверяет Пользователь). Все ответы на вопросы Q1–Q17, N1–N14 и предложения отчётов агента учтены; решения внесены в `docs/DECISIONS.md` и `docs/RULES.md`, открытых вопросов нет.
Источник правды по бизнес-логике: `docs/RULES.md`. Критерии приёмки и DoD здесь не пишутся: они появятся в плане этапа.

## 0. Общие правила карты

- **Коды этапов (CLAUDE.md):** этап N = код `SN` (S0…S10); аудиты `S2-audit`, `S6-audit`, `S9-audit`. Код ставится в заголовке issue (`S4: подача заявки`), имени ветки (`feature/s4-<коротко>`), коммитах (`feat(s4): …`), PR, записях AI-LOG и DECISIONS; метки issue `s0`…`s10`. Подэтапы 6a/6b/6c отдельных кодов не имеют (код S6, различаются названием PR).
- Этапы вертикальными срезами (бэкенд + интерфейс). Каждый этап = эпик-issue + дочерние issues на плане этапа.
- Код, меняющий поведение: issue → ветка `feature/<коротко>` → PR с `Closes #N`. Документы: коммит в main.
- Тест ссылается на пункт RULES комментарием `// RULES §N-k` (допустимо и `// RULES §N`). **ID утверждения `§N-k`:** k — порядковый номер пункта верхнего уровня в разделе RULES (вложенные пункты и примеры относятся к родителю и различаются короткой цитатой). Номера строк не используются. Новые пункты в существующих разделах RULES добавляются в конец раздела, чтобы ID не сдвигались; если сдвиг всё же произошёл, ссылки в тестах обновляются. Скрипт `scripts/trace-rules.mjs` собирает таблицу прослеживаемости grep-ом (отдельного документа нет) и падает на несуществующих `§N` и `§N-k`.
- Время только через Clock; исключения (RULES §9, DECISIONS): срок JWT и диспетчер outbox (интервал опроса, `next_attempt_at`, паузы между повторами) считаются по системным часам. Clock определяет только момент создания письма.
- **Изоляция e2e:** Playwright `workers: 1`; перед каждым сценарием скрипт `e2e:reset` (сброс данных БД, seed, очистка Mailpit через его API); нового эндпоинта в API нет. Демо-часы и сброс: Clock в демо-режиме читает строку состояния из БД при каждом вызове (без кэша в памяти) и создаёт её при отсутствии (значение = реальный момент первого обращения). Поэтому после сброса БД перезапуск API не нужен: первый же вызов Clock (в т.ч. из seed) инициализирует часы заново; нужные часы тест выставляет штатным механизмом. В API нет кэшей данных, переживающих сброс БД. **Проверить в этапе 0 экспериментом:** `prisma migrate reset` при подключённом API может оставить в пуле устаревшие соединения; если так, `e2e:reset` делает `TRUNCATE` всех таблиц приложения (кроме `_prisma_migrations`) и seed, либо перезапускает контейнер api. До этапа 3 seed и DB-часов нет: `e2e:reset` ограничивается сбросом данных, seed подключается в этапе 3. Решение фиксируется в DECISIONS.
- Тесты времени дополнительно с `TZ=America/New_York`.
- Хранение дней: целое число «половинок дня» (`halfDays INT`), не float.
- Первое начисление целочисленно: `halfDays = min(5, floor((n + 3) / 6))`, n = отработанные календарные дни от выхода до конца месяца (следует из §2, совпадает со всеми примерами таблицы §2).
- Ограничения БД (миграция с сырым SQL): `EXCLUDE USING gist (employee_id WITH =, daterange(start,end,'[]') WITH &&) WHERE (status='APPROVED')` (нужен `btree_gist`); пересечения «На согласовании» проверяются в приложении под блокировкой, потому что перенос по §5 пересекается со старым отпуском. При утверждении переноса в одной транзакции сначала старый → «Заменена переносом», потом новый → «Одобрена».
- Playwright: вход через UI в каждом контексте (sessionStorage не попадает в `storageState`).

- **RULES:** §1, §8 (Mailpit), §9 (Clock).
- **Зависимости:** нет.
- **Главный риск:** Windows (CRLF в скриптах, медленные volume), Alpine + Prisma (openssl); использовать Debian slim. Второй: `e2e:reset` при подключённом API (устаревшие соединения).
- **Тесты:** unit Clock (граница `2026-12-31T18:00Z` = 1 января в Бишкеке) под `TZ=America/New_York`; unit скрипта прослеживаемости (включая несуществующий `§N-k`); smoke `compose up` → `/health` = 200; `e2e:reset` два раза подряд, API после сброса отвечает без перезапуска. Playwright: smoke «страница открывается».

### S1. Архитектура и модель данных
- **Цель:** заполнить `architecture.md` (корень репозитория): ER (mermaid), `schema.prisma`, модули (auth, org, balance, vacations, approvals, mail/outbox, scheduler, calendar, events, clock), контракт API (OpenAPI), каталог ошибок (код + русское сообщение), схема SSE, схема планировщика (проход идемпотентный), политика блокировок, единая функция видимости `visibleTo(user)` для REST и SSE, функция «согласующий» (есть начальник → он, нет → HR). DECISIONS: обоснование стека (требование PDF), половинки дней, типы дат.

- **RULES:** §3, §5, §6, §7, §8, §9, §10.
- **Зависимости:** 0.
- **Главный риск:** переделка модели на этапах 5–6; митигация: прогнать каждый сценарий RULES на бумаге («сценарий → строки БД») до заморозки. Второй: дрейф миграции из-за сырого SQL.
- **Тесты:** integration на Postgres: пересекающиеся одобренные заявки падают; `start > end`; два года; дубль письма; дубль списания; второй ожидающий перенос; миграция на пустой БД; инвариант «один без начальника»; возврат сверх списанного отклоняется; возврат без ссылки на списание не создаётся; цепочка A→B→C сохраняется и читается (корень находится). Playwright: нет (нет интерфейса, обосновано).

- **RULES:** §1, §2, §3, §5, §6, §8.
- **Зависимости:** 0, 1.
- **Главный риск:** границы дат и `Date`; календарные даты как строки `YYYY-MM-DD`.
- **Тесты:** unit табличные по примерам §2 (5 строк таблицы, пример обрезки 20−5+2,5 → 15, пример §5-6 «выход 27 октября → 4 дня», напоминание 10 ноября → 5 ноября, суббота 14 ноября → среда 11); февраль и високосный год; выход 31 декабря и 1 января; тайбрейки n = 3, 9, 15, 21, 27; D = 1 число, D = 1 января, сегодня = 1 число (нет двойного счёта); начало вчера/сегодня/завтра/в прошлом году; списание 31 декабря против 1 января; возврат после обрезки; сдвиг даты выхода не трогает списания; отрицательный остаток не обрезается; fast-check: остаток кратен 0,5; прогон под `TZ=America/New_York`. Playwright: нет (нет интерфейса, обосновано).

### S3. Вход, роли, основа интерфейса, демо-часы
- **Цель:** логин и пароль (хеш), JWT 8 ч без refresh (по системным часам), токен в `sessionStorage`, при 401 экран входа «Сессия истекла, войдите снова» с возвратом на страницу; guard ролей (роли вычисляются из структуры, HR отдельный флаг), политика `visibleTo`; признак «доступ получен» (ставится при первом входе и в seed для сотрудников с выходом ≤ «сегодня»; вход до даты выхода без признака запрещён); seed на 11 пользователей и структуру команд с названиями «Фронт-отдел» и «Бэк-отдел» (имена и даты 2015–2021 даёт Пользователь); React-каркас: роутинг, защита страниц по роли, API-клиент (единая нормализация ошибок), обработка ошибок и пустых состояний; профиль на чтение (имя, дата выхода, название команды (пусто у директора, заместителя, HR, руководителей), руководитель); демо-часы: эндпоинт установки (дата и время, по умолчанию 09:00 COMPANY_TZ) только при флаге, постоянная полоса в шапке (значение часов, «остановлены», форма) для вошедших; публичная конфигурация с признаком демо-режима.
- **RULES:** §6 (доступ), §7, §9.
- **Зависимости:** 1.
- **Главный риск:** утечка видимости, если политика размазана по контроллерам; sessionStorage и e2e.
- **Тесты:** unit: хеш, guard; integration: вход (успех, неверный пароль), 401 без токена, истёкший токен, матрица «эндпоинт × роль»; **негативные §7:** сотрудник не получает чужие заявки и чужой календарь по прямому запросу; **эндпоинта установки часов нет (404) без флага**, сохранённое значение игнорируется (часы системные); с флагом начальное значение пишется один раз и не перезаписывается при перезапуске; часы не идут; признак доступа (сдвиг даты выхода в будущее после входа → доступ остаётся; без входа → доступа нет, пользователь через фикстуру; откат часов). Playwright: вход под тремя ролями, редирект с запретной страницы, сообщение при истёкшей сессии, полоса часов только при флаге, установка часов меняет значение; `fresh-clone` проверяет вход seed-пользователем.

### S4. Подача заявки
- **Цель:** форма (даты, backstopper, комментарий), остаток на сегодня и «на дату D» в одном месте, все проверки §3 с объяснениями (год, ≥ 1 раб. день, пересечения, остаток, до первого начисления, «в прошлом» + комментарий), атомарное создание под блокировкой, outbox и письмо «новая заявка» согласующему (директор → HR), «Мои заявки»; API списков с проверкой видимости (HR видит все на чтение); **справочник сотрудников «id + имя» для любого вошедшего (выбор backstopper, N13 a; без дат выхода, команд, остатков, руководителей);** **диспетчер outbox: периодический опрос по системным часам, `next_attempt_at`, нарастающие паузы между повторами, интервалы настраиваются переменными окружения (чтобы тесты не ждали); Clock диспетчером не используется**.
- **RULES:** §3, §4, §7, §8, §9, §10.
- **Зависимости:** 2, 3.
- **Главный риск:** расхождение прогноза и проверки (один код на оба); «сегодня» и даты берутся с сервера, не из браузера; диспетчер и демо-часы (диспетчер идёт по системному времени, создание письма по Clock).
- **Тесты:** integration на каждое правило и сообщение; конкурентные: две параллельные пересекающиеся заявки → проходит одна; двойной клик → одно письмо; негативные: чужие заявки недоступны; **Mailpit недоступен при замороженных демо-часах → письмо уходит ровно одно после восстановления (повтор по системному времени, Clock не двигается); два воркера диспетчера → одно письмо; перезапуск диспетчера между попытками → без дубля; письмо директора уходит HR; справочник сотрудников: ответ только id и имя, без токена 401, заявитель в backstopper отклоняется сервером**. Playwright: **«Сотрудник видит остаток дней на сегодня и сколько накопится к выбранной дате.»**; **«Заявка на больше дней, чем будет накоплено к началу отпуска, не проходит. Заявка, нарушающая правила дробления, не проходит с понятным объяснением.»** (один describe, два теста).

### S5. Согласование
- **Цель:** экран «Заявки на согласование» (сотрудник, даты, раб. дни, backstopper, комментарий, остаток, предупреждение о пересечениях), подтверждение и отклонение с необязательным комментарием, повторная проверка остатка, списание в журнал в той же транзакции, «уже обработана» (409), допуск HR для директора (предупреждение по одобренным отпускам прямых подчинённых директора и самого директора), письмо о решении, **обработчик события «заявка одобрена» в той же транзакции (в этапе 5 создаёт только письмо о решении; напоминания подключаются в этапе 7, до тех пор запись в `limitation`)**, у HR два раздела «Мои заявки» и «Допуск HR» (свою заявку HR согласовать не может: 403 с сообщением), события публикуются в шину, `seed:demo` («директор → допуск HR», «HR → заместитель директора», даты от Clock). **Отдельным PR после основного S5 (если S5 затянется, переносится в начало S6): календарь по роли без SSE (§7): эндпоинт на `visibleTo` и React-сетка месяца; сотрудник видит себя, руководитель прямых подчинённых и себя (с остатками подчинённых), HR всю компанию; только «Одобрена»; обновление при перезагрузке или переходе, поток SSE добавляется в S8.**
- **RULES:** §4, §6 (списание), §7 (календарь), §8, §10.
- **Зависимости:** 4.
- **Главный риск:** гонки двойного согласования; двойное списание; расхождение статуса и журнала.
- **Тесты:** integration: повторное решение → «уже обработана»; нехватка дней блокирует согласование, отклонение разрешено; ровно одно списание и ровно одно письмо; предупреждение учитывает только «Одобрена»; HR не согласует свою заявку (403); unit: маршрут согласующего. Playwright: **«Руководитель получает уведомление о новой заявке, сотрудник — о решении. По одному.»** (Mailpit API, двойной клик); **«Если в команде уже есть согласованный отпуск на пересекающиеся даты, руководитель видит это при согласовании.»**; две вкладки решают одну заявку → одно «уже обработана». **Календарь (PR без SSE): integration: «Одобрена» видна, «На согласовании» и «Отклонена» нет; чужой календарь по прямому запросу недоступен (сотрудник, руководитель 2 → команда 1); Playwright: сотрудник видит только свой календарь, руководитель команду, HR компанию.**

### S6. Отмена, перенос, дата выхода (три PR)
- **6a Отмена и отзыв:** **минимальный экран HR «Все заявки» (все заявки компании, статусы, пометки; одна кнопка «Отзыв» над начавшимся одобренным отпуском с обязательной датой выхода, только там, где действие допустимо; отдельной «Отменить» у HR нет, N14 a; статус результата «Отменена») и отмена сотрудником из «Мои заявки»;** сотрудник отменяет до начала (дни возвращаются полностью; для заявки «На согласовании» возвращать нечего); **возврат всегда привязывается к списанию корня цепочки (без переносов корень = сама заявка), сумма возвратов по списанию не превышает списанного;** HR отменяет и отзывает только после начала с датой выхода (от даты начала до окончания включительно; после окончания — отказ; относительно сегодня ограничений нет, N5: допустима дата в прошлом и в будущем в пределах отпуска); заявку «На согласовании» после начала не отменяет никто; HR до начала не отменяет; после отзыва статус «Отменена», пропадает из календаря целиком.

N4 (отмена заявки-переноса, когда старый отпуск уже начался) отложен «на конец»: отдельной логики и теста не вводится, действует буквальный текст §5 (отмена заявки «На согласовании» до её собственной даты начала сотрудником), случай записывается в `limitation`. **Цепочка переносов:** заявка-перенос хранит ссылку на исходную; при утверждении переноса переносимого переноса цепочка продолжается (A→B→C); отмена или отзыв действующего звена возвращает дни по списанию корня; прежние звенья не оживают и остаются «Заменена переносом».
- **6c Дата выхода:** минимальный экран HR «Остатки по сотрудникам» с изменением даты выхода; предупреждение при вводе; разовое сообщение; пересчёт; отрицательный остаток с цветным минусом; доступ не отзывается.

- **Зависимости:** 5.
- **Главный риск:** взаимодействие переноса, журнала и ограничения БД; **цепочки переносов (возврат не к той строке списания, двойной возврат, «оживление» прежних звеньев, перенос переноса)**; N4 отложен (отмена переноса, когда старый отпуск уже начался), тестами не закрывается.
- **Тесты:** integration: полный возврат до начала; возврат от даты выхода (выход на дату начала, в середине, на дату окончания, после окончания → отказ; дата выхода раньше сегодня и позже сегодня в пределах отпуска принимаются, возврат датируется по Clock в момент действия); негативные: отмена сотрудником после начала, отмена HR до начала, отмена заявки «На согласовании» после начала, отмена или отзыв старого отпуска при ожидающем переносе, утверждение переноса после начала; перенос не меняет остаток; повторная отмена → «уже обработана»; отмена и отзыв писем не создают; сдвиг даты выхода → остаток −N, доступ сохранён; **6a: экран HR показывает все заявки, кнопка «Отзыв» доступна только в допустимых состояниях (негативные: до начала HR кнопки не видит и получает отказ от API), отмена «На согласовании» не создаёт возврата; 6b (перенос): число рабочих дней должно совпасть, иначе отказ с объяснением; перенос только до начала; старый отпуск не участвует в проверке пересечений, а другие заявки сотрудника участвуют; отклонение и отмена переноса дают «Отклонена»/«Отменена» с пометкой «Старый отпуск остаётся», исходная остаётся «Одобрена»; перенос директора идёт к HR (письмо о заявке тоже HR, письмо о решении директору); перенос без backstopper отклоняется, прежний backstopper подставлен по умолчанию и заменяем; начало нового периода раньше сегодня отклоняется с объяснением («подайте обычную заявку»), начало сегодня принимается; цепочка A→B→C: после утверждения B→C отмена C возвращает дни по списанию A (корень), A и B остаются «Заменена переносом» и не оживают; повторная отмена C → «уже обработана», второго возврата нет; сумма возвратов по списанию A ≤ списанного; отзыв из C возвращает дни с даты выхода по списанию A**; **календарь (эндпоинт из S5): после отмены и отзыва отпуск пропадает из календаря целиком, после утверждения переноса в календаре новые даты, а «Заменена переносом» не показывается**. Playwright: **«Отмена согласованного отпуска возвращает дни в остаток. Отмена после начала возвращает только неиспользованные.»** (сотрудник до начала; HR после начала через демо-часы); **«Изменение даты выхода на работу пересчитывает накопление.»**.

### S7. Напоминания и планировщик
- **Цель:** планировщик (проход идемпотентный, Clock), напоминания в 09:00 по COMPANY_TZ сотруднику и руководителю (директору только себе), позднее одобрение → письмо сразу (только в момент одобрения; точка расширения в транзакциях одобрения этапа 5 и утверждения переноса 6b), статус «Одобрена» проверяется в момент отправки, перенос (старое не уходит, новое одно), при старте и на очередном проходе создаются просроченные напоминания (N7 a: дата напоминания раньше сегодня, отпуск не начался, «Одобрена», письма нет → письмо; дата напоминания сегодня и время до 09:00 → ждём 09:00; «сразу в любое время суток» только в момент одобрения). ### Как провести слепой аудит
1. **Подготовка.** Отдельный клон на помеченном коммите (`audit-1`/`audit-2`/`audit-3`). Удалить из клона CLAUDE.md, DECISIONS.md, AI-LOG.md, architecture.md, README.md, ROADMAP.md, TMP-*.md. Оставить код, тесты, `RULES.md` и PDF. Иначе CLAUDE.md подтянется автоматически, и сессия не будет слепой.
2. **Сессия.** Новая, без истории, желательно другой моделью. Права: чтение, запуск тестов, файлы только вне репозитория. Код проекта не править.
3. **Поручение.** (1) До чтения кода составить собственный список проверяемых утверждений из RULES.md и PDF (по отдельному утверждению, не по разделу). (2) Для каждого найти код и тест или записать «нет теста / нет реализации». (3) Попытаться сломать систему граничными входами и по возможности запускать их (тесты вне репозитория). (4) Всё, чего нет в RULES, помечать «в RULES не описано», а не додумывать.
4. **Формат результата.** Таблица: ID, серьёзность (критично / важно / замечание), утверждение (цитата RULES или номер пункта PDF), место (`файл:строка`), сценарий (вход → фактическое → ожидаемое), воспроизведение (текст теста), уверенность (ПОДТВЕРЖДЕНО запуском / ВОЗМОЖНО по чтению). Отдельно список неоднозначностей RULES.
5. **Обработка.** Пользователь разбирает находки. Подтверждённые → issue `audit-N`, сначала тест, потом исправление. Расхождение с RULES не правится молча: решение (код или правило; правило через DECISIONS).

**Дополнительно (аудит 3, безопасность):** перечислить все маршруты и сверить «маршрут × роль» с реальными ответами (включая IDOR); JWT: подпись, `alg: none`, `exp`, секрет без значения по умолчанию в репозитории; секреты: сканирование истории git (например, gitleaks), `.env` в `.gitignore`, в compose только демо-значения; белый список полей в DTO, параметризованные запросы (особенно сырой SQL), ограничение попыток входа, CORS, заголовки; порты Mailpit и Postgres только на localhost; эндпоинта демо-часов нет без флага (404); токен не попадает в URL и логи.

### Что ни один этап не покрывает полностью (осознанно или условно)

- Сотрудник после начала не отменяет отпуск сам (PDF подразумевает общую отмену): по RULES отмену после начала делает HR; сценарий e2e идёт через HR (DECISIONS 2026-10-20 22:36).
- Календарь команды для сотрудника: PDF не требует, RULES не даёт.
- Праздники, часовой пояс сотрудника, письма backstopper и HR, управление командами, кнопка «Вернуть реальное время»: сознательно вне объёма (RULES §11).
- Остаток в календаре руководителя и у сотрудника после смены даты выхода обновляется только при перезагрузке (DECISIONS, N8 (a)).
- «Ход работы во времени» не имеет этапа-владельца: покрывается непрерывно записями с временем и историей коммитов.

## 7. Общие договорённости

- Критерии приёмки и DoD пишутся в issue при плане каждого этапа, а не заранее.
- Закреплённый issue `Известные ограничения` создаётся в S0 и дополняется по ходу. Временная запись: S5 → до S7 напоминания при позднем одобрении не создаются (закрывается в S7). Дальше по списку из S10.
- Имена тестовых файлов: unit `*.spec.ts`, integration `*.int.spec.ts`, e2e `e2e/*.spec.ts`; в имени e2e-сценария точный текст пункта «Ожидаемого поведения».
- К S3 Пользователь готовит: имена 11 пользователей, даты выхода пяти руководящих (2015–2021), логины и пароли для README (в репозитории только демо-значения).
- Решения, принятые при составлении карты: backstopper переноса обязателен, подставлен прежний, можно заменить; начало переноса не раньше сегодня, «в прошлое» перенос не допускается (6b); справочник сотрудников «id + имя» для любого вошедшего (S1, S4); у HR одна кнопка «Отзыв» (6a); порядок проверки для демо в README: войти любым пользователем seed → выставить демо-часы на 2026-10-21 → `seed:demo` (S3, S10); напоминания по Clock, планировщик раз в минуту в обычном режиме (S7).
- Принято в S0: entrypoint api с `prisma migrate deploy` и идемпотентным seed; `.env.example` с `REMINDER_DAYS`, `COMPANY_TZ`, флагом демо-режима и `JWT_SECRET` (демо-значение, помеченное «только для демо»); `cross-env` для `TZ=`; `scripts/trace-rules.mjs` на Node (Windows без bash); остаток на экране согласования «доступно на дату начала заявки» (S5).
- Карта постоянный документ (`docs/ROADMAP.md`): после утверждения Пользователем меняется только записью в DECISIONS (с кодом ROADMAP) и правкой карты. До утверждения карты код не меняется (CLAUDE.md).
