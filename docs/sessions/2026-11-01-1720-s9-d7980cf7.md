## Вопросы (решаешь ты)

**1. Разовая проверка или постоянный шаг в CI?**
Рекомендую постоянный job `secrets` в CI: запуск Docker-образа с точной версией и digest, `fetch-depth: 0`, вся история HEAD на каждом PR и push в main.
- Почему вся история, а не только новые коммиты PR: 295 коммитов — это секунды, нет логики с диапазоном (`base..head`) и её ошибок, проверка не зависит от force-push и от того, откуда пришла база.
- Почему образ, а не gitleaks-action:
  - образ уже проверен локально, команда одна и та же локально и в CI;
  - action остаётся проприетарной сторонней зависимостью, хоть ключ для нас и не нужен;
  - его комментарии в PR требуют `pull-requests: write`, а у нас `contents: read`;
  - при переносе репозитория в организацию понадобился бы ключ.
- Разовый отчёт без CI не поймает секрет в следующих PR, в том числе в будущем коммите docs/sessions/ в S10.

**2. Как исключать демо-значения?**
Сейчас стандартные правила демо-значения не ловят, так что исключать из них нечего. Рекомендую `.gitleaks.toml` так:
- `[extend] useDefault = true` — все стандартные правила остаются;
- одно своё правило `compose-default-secret` на `${…(SECRET|PASSWORD|TOKEN|KEY)…:-значение}`;
- allowlist внутри этого правила с `regexTarget = "secret"` и точными `^demo-only-not-for-production$` и `^leave$`.

Почему не другие способы:
- allowlist по пути (`docker-compose.yml`, `.env.example`) скрыл бы любой настоящий секрет в этих же файлах, в том числе по стандартным правилам;
- общий regexp-allowlist действует на все правила;
- `.gitleaksignore` по fingerprint (коммит:файл:правило:строка) точен, но ломается при каждом изменении файла. Его стоит держать только для исторических находок, которые нельзя убрать (сейчас таких нет).

**3. Что делать, если найдётся настоящий секрет в истории?**
Рекомендую такой порядок:
1. Сразу ротировать секрет. Репозиторий публичный, после push значение считаем раскрытым.
2. Записать в DECISIONS и issue #2.
3. Добавить fingerprint в `.gitleaksignore` с комментарием-ссылкой на запись DECISIONS, чтобы CI позеленел.

`git filter-repo` и force-push по умолчанию не делать. Форки, кэш GitHub и клоны раскрытия не отменят, а переписанная история ломает ссылки на коммиты в PR, AI-LOG и DECISIONS. Переписывать только по твоему отдельному решению.

**4. Проверять ли docs/sessions/ этим же инструментом перед коммитом экспорта?**
Рекомендую:
- скрипт `scripts/scan-secrets.mjs` на Node (как `trace-rules.mjs`: в Windows нет bash, `$PWD`/`%cd%` в npm-скрипте не переносимы) и npm-скрипт `scan:secrets`. Скрипт запускает тот же образ: `dir` по рабочему дереву, включая неотслеживаемые файлы, плюс `git` по истории;
- одну строку в README: «перед коммитом экспорта: `npm run scan:secrets`; личные данные (email, пути) проверить вручную».

Отдельный шаг CI не нужен: после коммита docs/sessions/ job из вопроса 1 и так проверит их. Но CI срабатывает уже после push в публичный репозиторий, поэтому нужна локальная проверка до коммита. Экспорты дописываются (твоё сообщение), значит, проверка должна быть повторяемой, а не разовой.

Автоматическую проверку личных данных не делаю: gitleaks её не умеет, это отдельный инструмент.

Альтернатива проще: без скрипта, только инструкция в README с командой `docker run`. Минус: длинная команда с путями для Windows.

**5. Что записать в DECISIONS?**
Один пункт: gitleaks v8.30.1 (образ, digest) в job `secrets` по всей истории HEAD, своё правило для значений по умолчанию compose с исключением только точных демо-значений, порядок при настоящем секрете (вопрос 3), проверка экспортов (вопрос 4). Готовую запись со временем из `Get-Date` дам в конце.

**6. (дополнительно) Пометка Postgres в compose.**
`POSTGRES_PASSWORD` по умолчанию `leave` помечен как демо только в `.env.example`, в docker-compose.yml пометки нет. ROADMAP требует пометки для JWT_SECRET, а для Postgres прямо не требует. ## 3. Что значит «ротировать»

Ротировать секрет — выпустить новый и отозвать старый, чтобы утёкшее значение больше ничего не открывало. Удаление из файла или из истории git не помогает: значение уже могли скопировать.

Что это значит в нашем проекте:
- **Токен GitHub (`ghp_…`):** отозвать его в настройках GitHub и выпустить новый.
- **Пароль (Postgres, почта):** сменить там, где он действует.
- **Настоящий JWT_SECRET:** задать новое значение. Все токены, подписанные старым, перестанут действовать, и пользователи войдут заново.

Сейчас ротировать нечего: настоящих секретов не нашлось. Демо-значения публичны специально, их не ротируют.
