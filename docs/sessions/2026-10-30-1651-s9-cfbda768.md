## 1. Текст ошибки для `details.fields.password`

Пользователь этот текст не увидит. Экран входа показывает только `message` и `code`, `details.fields` он не выводит: `ErrorBox` → `describeProblem` в [problem.ts:51-53](apps/web/src/api/problem.ts#L51-L53). В форме будет «Некорректные данные запроса (VALIDATION_FAILED)». Текст поля читают те, кто вызывает API напрямую, и тесты.

Поэтому важнее, чтобы текст был точным, а не дружелюбным. Слово «байт» понятно не всем, поэтому предлагаю пояснить его на примере:

**`password: не длиннее 72 байт (латиница — до 72 символов, кириллица — до 36)`**

Начало `password:` сохраняет общий формат с `date: формат YYYY-MM-DD`. Если хотите короче, есть вариант `password: слишком длинный, не больше 72 байт`. Я за первый: он объясняет, почему кириллический пароль отклоняется уже на 37-м символе.

## 2. Как считать фиктивный хеш

Советую считать его один раз при первом обращении, сохранять в памяти и прогревать при старте в `onModuleInit`.

- **Почему один раз при первом обращении:** хеш считается той же функцией с тем же `ROUNDS`, что и настоящие. Если стоимость хеша когда-нибудь поменяют, фиктивный хеш поменяется вместе с ней.
- **Почему с прогревом:** без него первый запрос с неизвестным логином после каждого перезапуска считает хеш и сравнивает пароль. Он примерно вдвое дольше обычного и снова выдаёт, существует ли логин, хоть и один раз. Прогрев стоит около 70 мс при старте и 3 строки кода.
- **Другой вариант:** готовый хеш строкой в коде (`$2b$10$…`). Ни прогрева, ни подсчёта, но при смене `ROUNDS` хеш придётся пересчитать вручную. Тест это поймает, но лишняя ручная работа остаётся.

## 3. Web
