## Контракт

**`POST /vacations/{id}/cancel`**: тело пустое или `{}`, ответ `200 Vacation`.

Порядок проверок:
1. `400 VALIDATION_FAILED` — лишние поля в теле.
2. `404 NOT_FOUND` — заявки нет, она не видна или id некорректный.
3. `403 FORBIDDEN` — не владелец (руководитель или HR над чужой заявкой).
4. `409 ALREADY_PROCESSED` — статус не `PENDING` и не `APPROVED`.
5. *(6b: `409 PENDING_TRANSFER_BLOCKS`)*
6. Если сегодня ≥ даты начала: для `APPROVED` → `403 CANCEL_STARTED_BY_EMPLOYEE`, для `PENDING` → `422 CANCEL_PENDING_AFTER_START`.

Что пишется:
- `APPROVED`: статус `CANCELLED`, `cancelledBy/At` (Clock), `REFUND(halfDays = workDays·2, refundOfId = списание корня, occurredAt = Clock)`. После коммита событие `vacation.cancelled {by: EMPLOYEE}`.
- `PENDING`: только статус `CANCELLED`, без возврата и без события.
- Писем нет ни в одном случае.

**`POST /vacations/{id}/recall`**: тело `{returnDate: "YYYY-MM-DD"}`, ответ `200 Vacation`.

Порядок проверок:
1. `400 VALIDATION_FAILED`.
2. `404 NOT_FOUND`.
3. `403 FORBIDDEN` — не HR. *(Сюда же встанет отказ по В2, если выберете вариант «б».)*
4. `409 ALREADY_PROCESSED` — статус `CANCELLED` или `REPLACED`.
5. `422 RECALL_NOT_APPROVED` — статус `PENDING` или `REJECTED`.
6. `422 RECALL_NOT_STARTED` — сегодня < даты начала.
7. *(6b: `409 PENDING_TRANSFER_BLOCKS`)*
8. `422 RECALL_DATE_OUT_OF_RANGE`.

Что пишется: статус `CANCELLED`, `cancelledBy/At`, `returnDate`, `REFUND(halfDays = refundHalfDays(start, end, returnDate))`. Возврат может быть 0, например при дате выхода в выходной в конце отпуска. Событие `vacation.cancelled {by: HR_RECALL}`.

**Проектные решения (предлагаю записать в DECISIONS):**
- Отзыв по `REJECTED` даёт `RECALL_NOT_APPROVED`, а не `ALREADY_PROCESSED`: заявка не была одобрена.
- Отзыв по `CANCELLED` или `REPLACED` даёт `ALREADY_PROCESSED`.

**Блокировки (architecture §6, как в approvals):**
1. `employeeId` читается без блокировки.
2. В транзакции: `User ... FOR NO KEY UPDATE`, затем звенья цепочки до корня по возрастанию id. Цепочка читается до блокировки рекурсивным CTE по `replacesId`; в 6a это одно звено, но код общий, чтобы 6b его не переделывал.
3. После блокировки статус перечитывается.
4. Вставка `REFUND`: триггер сам блокирует списание корня и проверяет сумму возвратов.
5. Если сработал уникальный индекс `one_refund_per_vacation` (ошибка `P2002`), ответ `409 ALREADY_PROCESSED`.

**`actions`** (только подсказка интерфейсу, права проверяет сервер):
- `cancel` — зритель владелец, статус `PENDING`/`APPROVED`, сегодня < даты начала.
- `recall` — зритель HR, статус `APPROVED`, сегодня ≥ даты начала (с поправками по В2 и В3).
