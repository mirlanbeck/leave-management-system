**Q1. Mailpit недоступен при отправке письма. Как это сочетается с «ровно одно письмо»?**
- (a) Потеря: одна попытка, при ошибке письмо теряется. Нарушает «по одному» на деле.
- (b) Исходящая очередь (outbox) в БД: строка письма пишется в **той же транзакции**, что и смена статуса. С ключом уникальности «тип + id отпуска + получатель» (§8) это даёт «ровно одно». Отдельный воркер шлёт письма с повторами (например, до N попыток с нарастающей паузой). Пользователю ошибка не показывается, решение по заявке не откатывается.
- (c) Отправка внутри запроса: при недоступном Mailpit показывать ошибку и откатывать решение. Связывает бизнес-действие с почтой, ломает «решение принято».
- **Рекомендация: (b).** Остаточный риск: сбой между ответом SMTP и пометкой «отправлено» даёт дубль. Записать в README как известное ограничение, это стандартное «at-least-once плюс уникальность».

- Аудит 1 идёт параллельно с этапом 3.

**Находка по модели данных (важно для этапа 1).** Ограничение «нет двух пересекающихся заявок одного сотрудника в статусах На согласовании и Одобрена» нельзя повесить на БД «в лоб»: по §5:79 перенос (На согласовании) по определению пересекается со старым отпуском (Одобрена). Предлагаю такую схему:
- На уровне БД: `EXCLUDE USING gist (employee_id WITH =, daterange(start,end,'[]') WITH &&) WHERE (status='APPROVED')`. Нужно расширение `btree_gist`, это сырой SQL в миграции, потому что Prisma такие ограничения не описывает.
- Пересечения «на согласовании против одобренных/на согласовании» проверяются в приложении под блокировкой (`SELECT … FOR UPDATE` на сотруднике или advisory lock).
- Утверждение переноса: в одной транзакции сначала старый → «Заменена переносом», потом новый → «Одобрена». Порядок важен, потому что ограничение проверяется после каждого оператора.

**Дробные дни (шаг 0,5).** Хранить целое число «половинок дня» (`halfDays INT`): 2,5 дня = 5, обрезка 15 = 30. Вместо float или Decimal. Выгода: нет ошибок округления, сравнения точные. Первое начисление считается чисто целочисленно: `halfDays = min(5, floor((n + 3) / 6))`, где n — отработанные календарные дни. Эта формула выводится из §2 (n/30·2,5 в половинках) и совпадает со всеми примерами таблицы §2. Тайбрейк «вверх» даёт случаи n = 3, 9, 15, 21, 27. Решение принять и записать на этапе 1.
