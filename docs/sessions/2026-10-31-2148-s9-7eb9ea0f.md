## 1. Что в коде сейчас

**Порядок проверок в `POST /auth/login`**

**Где встаёт проверка лимита.** В начале `AuthService.login`, до шага 2. Для любого логина путь одинаковый: без обращения к БД и без bcrypt, сразу 429. Поэтому ни ответ, ни время при блокировке не выдают, существует ли логин. Это верно только если неизвестные логины считаются и блокируются так же, как известные (вопрос 5). Выравнивание S9-b не страдает: незаблокированный путь не меняется.

**Какой IP видит api за nginx**

- Если включить `trust proxy`, то при прямом доступе на :3000 ([docker-compose.yml:51-52](docker-compose.yml#L51-L52), только 127.0.0.1) `X-Forwarded-For` можно подставить любой.

## 2. Вопросы к вам

Это решения не из RULES, поэтому решаете вы. К каждому вопросу — моя рекомендация.

1. **Ключ лимита.** Рекомендую **только логин**, ровно в том виде, в каком его прислали, и для неизвестных логинов так же. IP не используется: в стенде он один на всех (см. раздел 1).
   - Чтобы длинный логин не раздувал память, в Map храню SHA-256 от логина. В DTO длина логина не ограничена — это отмечено в конце, отдельная задача.
   - Плата: зная логин, можно на время заблокировать вход чужому пользователю. Это остаётся известным ограничением (issue #2).
2. **Порог и окно.** Рекомендую **5 неудач за 15 минут → блокировка на 15 минут от пятой неудачи**, фиксированная, без нарастающей паузы.
   - Успешный вход сбрасывает счётчик.
   - Попытки во время блокировки получают 429, не считаются и блокировку не продлевают: иначе можно держать человека заблокированным бесконечно.
   - Неудача засчитывается до bcrypt, а не после: иначе 100 параллельных запросов проверили бы 100 паролей. Успех потом снимает этот резерв.
3. **Ответ.** Рекомендую **429, новый код `AUTH_TOO_MANY_ATTEMPTS`**, заголовок `Retry-After` в секундах и `details.retryAfterSeconds`. Ответ одинаков для существующего и несуществующего логина. Ответ 401 без отличия хуже: человек с верным паролем не поймёт, почему не может войти.
4. **Хранение.** Рекомендую **в памяти процесса**, как и SSE-подписки. api в стенде один. Перезапуск api снимает блокировки — это записать в README и issue #2. Хранение в БД означало бы миграцию и запись в БД на каждую неудачу, а для демо это лишнее.
5. **Что считать попыткой.**
   - Неверный пароль — да.
   - Неизвестный логин — да, иначе блокировка выдаёт существование логина.
   - Ошибка валидации (400, 72 байта) — нет: до сервиса она не доходит.
   - «До даты выхода» (403) — не неудача: пароль верный, поэтому рекомендую считать её успехом и сбрасывать счётчик.
6. **Тесты.** Рекомендую **без флага и без отдельного порога**: честнее, когда тесты идут с боевым порогом. Это возможно, потому что e2e и int под порог не попадают (раздел 1).
   - Окно в int проверяется подменой часов лимита FakeClock через `createTestApp(…, customize)`.
   - В e2e:reset сброс не нужен. Для этого понадобился бы служебный маршрут, а это расширение задачи.
7. **Текст.** Рекомендую «Слишком много неудачных попыток входа. Повторите через {n} мин.». Число минут сервер округляет вверх. Экран показывает текст как есть, правки web не нужны.
8. **Правка RULES.** Рекомендую **дописать** в §7-1 и §9-1 (тексты в разделе 5). Тогда метки тестов будут `// RULES §7-1, §9-1`, как в S9-b. Без правки метки будут как в S9-f: `// ROADMAP S9 (аудит 3, безопасность: лимит попыток входа); DECISIONS <время>; аудит 3, F-3`.

   - **(а)** в контроллере взять `@Res({ passthrough: true })` и поставить заголовок перед тем, как ошибка уйдёт в фильтр. Фильтр затем пишет статус и тело в тот же `res`, и заголовок сохраняется.

## Агент · 16:03

Лучше всего **после закрытия S9 (multer, `npm audit`, gitleaks) и до S10**.

**Почему не раньше:**
- **Безопасность важнее.** Задачи S9 закрывают находки аудита. Если в них всплывут правки зависимостей, сборки web или CI (а `npm audit` касается и `apps/web`), то сделанный до них UI придётся проверять заново.
- **Конфликты веток.** Пока идут задачи S9, правки интерфейса будут пересекаться с ними в файлах, тестах и документах.

**Почему не позже S10:**
- В S10 README описывает экраны: порядок шагов проверяющего, как проверить две вкладки, демо-часы. Если менять интерфейс после README, его придётся переписывать.
- Итоговый `fresh-clone` и экспорт сессий должны идти уже на финальном виде интерфейса.

**Что учесть заранее, это влияет на объём:**
1. **Тексты защищены правилами.** Часть надписей задана в RULES дословно: «Мои отпуска», «В этом месяце отпусков нет» (§7-2) и формулировки ошибок с пометкой «RULES» в architecture §8. Их нельзя менять без правки RULES через DECISIONS. Остальные тексты (пункты меню, заголовки, кнопки) — проектные решения из DECISIONS, например 2026-10-28 10:58 по экрану «Согласование». Их менять можно, но каждое изменение — новая запись в DECISIONS.
2. **e2e привязаны к текстам.** Сценарии ищут элементы по ролям и подписям: `getByRole('heading' | 'link', { name })` встречается 16 раз, ещё есть `getByLabel` и тексты кнопок. Переименование вкладок потянет правку e2e. Это нормально, но объём больше, чем кажется.
3. **Отдельный эпик.** Такой этап в ROADMAP не запланирован, а CLAUDE.md (правило 7) запрещает расширять задачу молча. Нужен отдельный код этапа или эпика и запись в ROADMAP. Это решаете вы.
4. **Начать с разбора, а не с правок.** Первым шагом сделать обзор текущих экранов: внешний вид, узкий экран, клавиатура, контраст, понятность названий.
