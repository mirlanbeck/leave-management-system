## Ошибки и неверные допущения

1. **Тест инварианта «один директор» был неверен.** В плане был «второй пользователь без начальника → seed падает». В миграции S1 уже есть `User_single_root_idx` ([migration.sql:165](apps/api/prisma/migrations/20261023163539_s1_data_model/migration.sql#L165)), и вторая вставка упадёт в БД раньше seed. Для директора seed должен проверять ровно один, то есть защищаться от нуля. Ограничения «не более одного HR» в БД нет, поэтому негативный тест делается на HR: второй `isHr` в БД → seed падает.
2. **Прогон под `TZ=America/New_York` не охватит `seed.int.spec.ts`.** Скрипт `test` исключает `*.int.spec.ts` ([package.json:16](apps/api/package.json#L16)), а `test:tz` запускает именно его. Критерий «прогон под TZ» в issue остался бы формальным. Чистую часть нужно вынести в unit-тесты:
   - `seed-data.spec.ts`: уникальные логины, один корень, один HR, команды только у сотрудников 1–6, совпадение с таблицей README;
   - вычисление `accessGranted` по `today` для границ даты, включая 2026-10-12.
   Integration-тест остаётся для работы с БД и идемпотентности.
3. **Seed нельзя тестировать как скрипт.** Сейчас это `main()` с побочным эффектом. Нужна экспортируемая `runSeed(db, clock, env)` и запуск только при `require.main === module`. В плане этого не было. Выбор часов тоже должен быть внутри: `DEMO_MODE === 'true'` через `isDemoMode` даёт `DbClock`, иначе `SystemClock`. Пояс берётся через `companyTz(env)`, как в [auth.service.ts](apps/api/src/auth/auth.service.ts), чтобы вход и seed не разошлись.
4. **Падение инварианта могло навсегда сломать запуск.** Entrypoint идёт под `set -eu`. Если проверка выполняется после коммита, битая БД оставит строки и api не стартует при каждом перезапуске. Всё делается в одной транзакции: создание, проверка инвариантов, при нарушении откат.
5. **Гонка при создании.** Seed запускается при каждом старте api и ещё из `e2e:reset`. «Найти и создать» может дать нарушение UNIQUE по логину. Нужен `INSERT ... ON CONFLICT (login) DO NOTHING` или `createMany({ skipDuplicates })`.
6. **`e2e:reset` через `docker compose exec` надо делать аккуратно.** Нужны `-T` (нет TTY), корректный `cwd` (корень репозитория) и понятная ошибка, если контейнер api не запущен. Сейчас [reset.mjs](e2e/reset.mjs) может запускаться из `e2e/`. [reset.spec.ts](e2e/reset.spec.ts) вызывает `resetAll()`, поэтому правки затронут и его. Его утверждения (проба обнулена, Mailpit пуст, health 200) остаются верными, но их надо перепроверить прогоном. В план это не попало.
7. **Побочный эффект для часов.** TRUNCATE стирает и `ClockState`, а seed при `DEMO_MODE=true` создаёт её заново с реальным моментом. После каждого `e2e:reset` демо-часы возвращаются к реальному времени. Это соответствует DECISIONS (реальный момент первого запуска), но тесты не должны ждать, что выставленные часы переживут reset. Я об этом не упомянул.
8. **Неясная формулировка теста 5.** «Каждый входит, кроме случая…» запутывает. Нужно так: при часах после 2026-10-12 входят все 11. При часах 2026-10-11 `liam` получает отказ входа, а остальные входят.
9. **Не проверил имена в политике.** Я написал `visibleTo`, а в [policy.ts](apps/api/src/org/policy.ts) есть `rolesOf`, `scope` и `canSee`. Тест 6 будет работать через `scope(viewer, directReportIds)` и `canSee`. Нужно заполнять `directReportIds` из реальной структуры seed.
10. **Тест 7 (README = seed) тоже должен быть unit-тестом без БД.** Иначе под `TZ` и `npm test` он не пойдёт. Он входит в п.2.

## Часы в e2e: как сделать надёжно

Вариантов три, и лучше их сочетать.

| Вариант | Надёжность | Недостаток |
|---|---|---|
| **A. Каждый сценарий сам выставляет часы первым шагом** | Явно, но держится на дисциплине | Один забытый шаг — тест зависит от реальной даты запуска. Это нарушение изоляции. |
| **B. `e2e:reset` сам ставит часы на фиксированную дату по умолчанию** | Детерминированно, забыть нельзя | Сценарий с другой датой всё равно ставит её сам. |
| **C. Часы задаются через env при старте** | — | Противоречит RULES §9 (начальное значение — реальный момент первого запуска). Не подходит. |

**Рекомендация: B плюс A только для отклонений.**

- `e2e:reset` делает три шага: TRUNCATE, затем запись `ClockState` напрямую в БД (тот же механизм, что `setDbClock` в int-тестах), затем seed. Часы идут до seed, поэтому `accessGranted` считается на ту же дату и не зависит от реальной.
- Значение по умолчанию — **2026-10-21 09:00 Бишкек** (`2026-10-21T03:00:00Z`). Это дата из README для демо и сценария Сотрудника 3 («до 1 ноября заявку подать нельзя»). `liam` при ней входит, потому что выход 2026-10-12 уже наступил.
- Сценарий, которому нужна другая дата, ставит её сам через кнопку или эндпоинт часов. Остальные получают детерминированную дату без дополнительных шагов.
- Сценарии «до выхода» в S3-d можно проверять так: ставим часы на 2026-10-11, затем reset или seed.
