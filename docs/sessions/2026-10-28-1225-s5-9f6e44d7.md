## Вопросы

**Q1. Параметры GET /calendar.** В architecture §7 у запроса два обязательных параметра: `from` и `to`. Я бы их и оставил, а месяц пусть считает клиент. Ещё нужно договориться о трёх вещах:
- **Что попадает в ответ.** Предлагаю отдавать отпуск, если он хотя бы частично пересекается с `[from, to]`. Даты отпуска не обрезаются по границам месяца.
- **Проверки запроса.** Неверная дата, `from > to` или лишний параметр дают `400 VALIDATION_FAILED`. Нужен ли предел длины диапазона? Предлагаю не более 366 дней, иначе 400.
- **Порядок записей.** По `startDate`, затем по имени, затем по `id`.

**Q2. Откуда клиент берёт «сегодня» для начального месяца.** По правилу «время через Clock» браузерные часы брать нельзя. Есть два варианта:
- (a) брать `today` из уже существующего `GET /me/balance`; контракт API не меняется;
- (b) добавить поле `today` в схему Calendar.

Рекомендую (a).

**Q3. Что значит «чужой календарь по прямому запросу».** У `GET /calendar` нет параметра `employeeId`, поэтому запросить календарь конкретного человека нельзя. Предлагаю проверять это двумя тестами:
- ответ сотрудника не содержит чужих одобренных отпусков, хотя они есть в этом диапазоне;
- запрос `?employeeId=<чужой>` получает 400, потому что лишние параметры query запрещены.

Для пары «руководитель 2 → команда 1» то же самое: в ответе manager2 нет отпусков employee1. Такая трактовка подходит?

**Q4. Где календарь в интерфейсе.**
- (a) Отдельная страница `/calendar` с пунктом меню «Календарь» для всех ролей. HR видит на ней всю компанию, а `/hr` остаётся заглушкой до S6c. Тогда меню будет «Профиль, Отпуск, [Согласование], Календарь, [HR]», и проверку состава меню в web-shell.spec придётся поправить.
- (b) Календарь HR разместить на `/hr` вместо заглушки, остальным ролям дать отдельную страницу.

Рекомендую (a): тогда остатки и смена даты выхода в S6c пойдут на `/hr` и не будут мешать календарю.

**Q5. Как выглядит сетка.** Предлагаю таблицу: строки — сотрудники, столбцы — дни месяца с 1 по 28–31. Выходные затенены, дни отпуска закрашены, в подсказке период. В строки попадают только те, у кого в этом месяце есть одобренный отпуск. Под сеткой список «ФИО, команда, с … по …»: он доступен скринридеру, и по нему удобно проверять e2e. Альтернатива — классический календарь из 7 столбцов с именами в ячейках, но при 11 сотрудниках он плохо читается. Принимаешь вариант «строки = сотрудники»?

**Q6. Остатки подчинённых (Calendar.balances).** Предлагаю:
- отдавать остатки всех прямых подчинённых, а не только тех, кто в отпуске в этом месяце;
- считать остаток на сегодня через тот же `BalanceService`, что и `/me/balance`;
- поле только у руководителя; у сотрудника и у HR без подчинённых его в ответе нет. Остатки для HR — это S6c, `GET /hr/balances`;

Дополнительно: заместитель увидит остаток HR, потому что HR — его прямой подчинённый (§7-2). Это ожидаемо?

Советую отдельную страницу «Календарь» в меню у всех, включая HR.
