## Как устроено

- **Получатели и постановка в очередь.** Новый файл `mail/decision-mail.ts` с функцией `enqueueDecisionMail(tx, vacation: VacationRow)`. Получатель всегда `vacation.employeeId`, у директора тоже он сам. Backstopper и HR как наблюдатель письма не получают. Состав получателей по architecture §3 решает модуль `mail`. `createdAt = vacation.decidedAt`, поэтому момент письма и момент решения — одно значение Clock. Отдельного `now` нет, и разойтись им не из чего.
- **Хук.** Новый файл `approvals/vacation-approved.hook.ts`, Nest-провайдер с методом `onVacationApproved(tx, vacation)`, сигнатура как в architecture §4 и §9. В S5 он только вызывает `enqueueDecisionMail`.
  - S7 добавит в него немедленный `REMINDER`. «Сегодня» берётся из `decidedAt` и `COMPANY_TZ`, `APP_ENV` уже доступен через DI.
  - S6b вызовет тот же хук из ветки утверждения переноса в той же транзакции.
  - Транзакцию для этого переделывать не придётся.
- **`decide`.** После `vacation.update` внутри `$transaction`: при approve вызывается `hook.onVacationApproved(tx, updated)`, при reject — `enqueueDecisionMail(tx, updated)`. `VACATION_INCLUDE` уже содержит всё нужное для письма: `employee.fullName`, `managerId` (признак директора), `decidedBy.fullName`.
- **Ровно одно письмо (§10-1).** Защита трёхслойная:
  1. Блокировка `User` → `Vacation` и повторная проверка статуса: второй approve или reject получает 409 до постановки письма.
  2. Транзакция проигравшего откатывается вместе с его письмом.
  3. Последняя линия — ключ `(DECISION, vacationId, recipientId)` с `ON CONFLICT DO NOTHING`. Одобрение и отклонение — один тип, поэтому двух писем о решении по одной заявке не будет даже при ошибке в коде.
