# leave-management-system

Full-stack employee leave management system with leave balance tracking, approval workflows, team calendars and HR administration

## Как сделан проект

- **Инструмент:** Claude Code (расширение для VS Code).
- **Модель:** Claude Sonnet 5.5.
- **Почему:** Claude Code работает прямо в репозитории: читает код, правит файлы, запускает команды и тесты, а каждая сессия сохраняется в виде JSONL-лога с временными метками. Sonnet 5.5 выбран как баланс качества и расхода лимитов тарифа Pro.
- **Вне Claude Code:** отдельные вопросы (разбор требований, расход лимитов, формулировки для документации) обсуждались в чате claude.ai. Код проекта этим чатом не писался.
- **Лог работы:** `DECISIONS.md` (решения с датой и временем), история коммитов, экспорт сессий Claude Code в `docs/sessions/`.

## Требования к окружению

Указаны только значения, измеренные на машине разработки 2026-10-23. Минимальные версии Docker и Compose, другие ОС и объём RAM для сборки образов не проверялись.

**Проверено на:** Windows 11 Pro 10.0.26200 (64-bit), Docker Desktop (движок на WSL2, `6.18.33.2-microsoft-standard-WSL2`), 31,5 ГБ RAM, виртуальная машина Docker видит 24 CPU и 15,4 ГиБ.

| Что                             | Измеренное значение                                                                                              |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Docker Engine                   | 29.8.2 (`docker version`, client и server)                                                                       |
| Docker Compose                  | v5.5.1 (`docker compose version`), Compose v2+ синтаксис                                                         |
| Node.js (для тестов вне Docker) | 24.21.0, npm 11.6.2                                                                                              |
| Образы проекта                  | api 872 МБ, web 280 МБ; postgres 625 МБ, mailpit 60 МБ (`docker images`)                                         |
| Память в простое после старта   | api 91,6 МиБ, postgres 36,3 МиБ, web 20,8 МиБ, mailpit 8,9 МиБ, всего около 158 МиБ (`docker stats --no-stream`) |

**Порты (только 127.0.0.1):** web 8080, api 3000, Postgres 5432, Mailpit 8025 (интерфейс) и 1025 (SMTP). Порты должны быть свободны.

**Запуск:** `docker compose up` из корня репозитория (`cp .env.example .env` не нужен, демо-значения заданы в `docker-compose.yml`). Страница: http://localhost:8080, проверка API: http://localhost:3000/health, почта: http://localhost:8025. Данные Postgres лежат в именованном томе `pgdata`; полный сброс: `docker compose down -v`.

**Проверка запуска:** `npm run smoke:compose` (поднимает стек, проверяет healthcheck, порты, /health, перезапуск api, повторный `up`, том Postgres).

**Integration-тесты и миграции вне Docker:** `npm run test:int` и `prisma migrate dev` запускаются на хосте и требуют `DATABASE_URL` (по умолчанию её нет). Сначала поднимите Postgres: `docker compose up -d postgres`. Затем:

    npx cross-env DATABASE_URL=postgresql://leave:leave@127.0.0.1:5432/leave npm run test:int

`cross-env` нужен, чтобы команда одинаково работала в PowerShell, cmd и bash. Unit-тесты (`npm test`) БД не требуют.

### Работает

S0: `docker compose up` поднимает postgres, mailpit, api и web, у каждого healthcheck; `GET /health` проверяет БД; миграции и seed (пока пустой) при старте api; страница web открывается и показывает статус API; Clock и `scripts/trace-rules.mjs` (S0-a). CI (GitHub Actions): lint, typecheck, unit и integration с Postgres в двух часовых поясах (по умолчанию и `America/New_York`), trace-rules, e2e, `fresh-clone`; `npm run e2e:reset` (TRUNCATE таблиц приложения и очистка Mailpit, API перезапуска не требует); Playwright с одним воркером и smoke «страница открывается» (S0-c). Эпик S0 закрыт (PR #4, #5, #7, #9). Следующий этап: S1.

S1 (S1-a, схема и ограничения БД): таблицы User, Vacation, LedgerEntry, OutboxMessage и ClockState (`apps/api/prisma/schema.prisma`, миграция `s1_data_model`); ограничения БД: нет пересечения одобренных отпусков, одна заявка в пределах года, минимум 1 рабочий день, один пользователь без начальника, один ожидающий перенос на отпуск, одно списание и один возврат на заявку, возврат привязан к списанию корня цепочки переносов и не превышает списанного, одно письмо на «тип + отпуск + получатель», одна строка состояния демо-часов; временная таблица `AppMeta` удалена. Integration-тесты на Postgres (`npm run test:int`, в CI в двух часовых поясах); в CI проверка, что миграция не расходится со схемой (`db:drift`). S1-b (документ [architecture.md](architecture.md)): ER-диаграмма и описание таблиц по схеме; список ограничений БД и что остаётся приложению; 10 модулей; согласующий (`approverOf`) и видимость (`visibleTo`) для REST и SSE; политика блокировок; контракт API (OpenAPI внутри документа, 19 маршрутов для S3–S8, роли по маршрутам); каталог из 37 ошибок с пунктами RULES; события и SSE; схема планировщика и диспетчера outbox; таблица «сценарий → строки БД»; обоснование стека. Кода нет: это контракт для S2–S8. Эпик S1 закрыт (PR #13 и этот PR).

S2: чистая доменная логика (баланс, «доступно на D», обрезка, возврат, дата напоминания, проверки формы) с 162 тестами в двух часовых поясах (по умолчанию и `America/New_York`), код в `apps/api/src/domain`. Следующий шаг: Аудит 1, затем S3.

### Не работает

Бизнес-функций для пользователя (вход, заявки, баланс на экране) нет: схема БД и чистая доменная логика (S2) есть, но к API и БД не подключены. «Хотя бы один пользователь без начальника» БД не гарантирует (только «не больше одного»): это проверит seed в S3. Вход seed-пользователем в `fresh-clone` и seed в `e2e:reset` появятся в S3. Проверка `/health` после `prisma migrate reset` ограничена `SELECT 1` (DECISIONS 2026-10-23 19:41); на запросах к таблицам приложения её перепроверим в S3. API и вход не реализованы: `architecture.md` описывает контракт, а не готовые маршруты; mermaid-диаграммы в нём рендерятся на GitHub и в превью VS Code.

S2: ни API, ни БД, ни интерфейса поверх домена нет. Проверки пересечений и остатка остаются в S4. Аудит 1 (слепой) после S2 ещё не проведён.

### Видение формулировок требований (ПОДТВЕРЖДАЮ этот подпункт, когда эти разделы реально заработают (S6 и S8). Сейчас это просто заготовка чтобы не забыть.)

Календарь команды виден руководителю (прямые подчинённые и он сам) и HR (вся компания). Сотрудник видит только свои отпуска (RULES §7).
Начавшийся отпуск сотрудник сам отменить не может: это делает HR отзывом с датой выхода, возвращаются неиспользованные рабочие дни (RULES §5; DECISIONS 2026-10-20 22:36).
