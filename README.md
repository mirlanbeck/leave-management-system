# Отпуска (leave-management-system)

Сервис учёта отпусков для компании. Сотрудник видит, сколько дней ему полагается сегодня и сколько накопится к выбранной дате, и подаёт заявку. Руководитель подтверждает или отклоняет её с комментарием и видит пересечения с отпусками команды. HR видит календарь и остатки по всей компании, меняет дату выхода на работу и отзывает из начавшегося отпуска. Письма (о новой заявке, о решении, напоминание) уходят в локальную заглушку почты, календарь обновляется у всех открытых клиентов без перезагрузки.

Тестовое задание Mad Devs. Репозиторий: https://github.com/mirlanbeck/leave-management-system. Запуск локально через Docker, без облака.

**Как читать этот README:** правила → запуск → демо-пользователи → как проверить → как устроено и почему такой стек → соответствие заданию → тесты → состояние проекта → видение формулировок → как делали и ход работы во времени.

## Правила предметной области

Правила (накопление, дробление, согласование, отмена и перенос) в задании оставлены на усмотрение автора. Они описаны в [docs/RULES.md](docs/RULES.md): это единственный источник правды, код и тесты ссылаются на его пункты (`// RULES §N-k`). Коротко:

- **Единицы.** Дни считаются в рабочих днях (пн–пт), праздники не учитываются; шаг остатка 0,5 дня. Один часовой пояс компании `Asia/Bishkek` (RULES §1).
- **Накопление.** 30 рабочих дней в год: по 2,5 дня 1-го числа каждого месяца. Первое начисление пропорционально отработанным дням первого месяца (делитель 30, округление до 0,5, ничья вверх). На 1 января остаток обрезается до 15 дней (RULES §2).
- **Заявка и дробление.** Дробление свободное: заявка в пределах одного календарного года, не меньше 1 рабочего дня и без пересечения со своими заявками; backstopper («заменяющий» или ответственное лицо в отсутствие сотрудника) обязателен; в задании его нет, это дополнение проекта. Заявка проходит, только если дней хватает **к дате начала** отпуска; иначе или при нарушении формы — отказ с объяснением (RULES §3).
- **Согласование.** Согласует непосредственный руководитель, заявки директора — HR («допуск HR»). Остаток проверяется повторно, дни списываются сразу целиком. Руководитель видит предупреждение о пересечении с одобренными отпусками команды (RULES §4).
- **Отмена и перенос.** До начала отпуска сотрудник отменяет сам, дни возвращаются полностью. Начавшийся отпуск сокращает HR отзывом с датой выхода: возвращаются только неиспользованные рабочие дни. Перенос — новые даты с тем же числом рабочих дней, согласуется как заявка (RULES §5).
- **Дата выхода на работу** — дата начала работы в компании (в профиле); от неё считается накопление. Меняет только HR, накопление пересчитывается (RULES §6). Не путать с датой выхода из отпуска при отзыве (RULES §5).
- **Письма.** Новая заявка → согласующему, решение → автору, напоминание за `REMINDER_DAYS` рабочих дней (по умолчанию 3) в 09:00 сотруднику и руководителю, всё по одному (RULES §8).

Как понимались неоднозначные места задания — раздел [«Видение формулировок требований»](#видение-формулировок-требований).

## Быстрый старт

1. Установлен Docker с Compose v2, свободны порты 8080, 3000, 5432, 8025, 1025 (подробнее — [«Требования к окружению»](#требования-к-окружению)).
2. Из корня репозитория: `docker compose up`.
3. Откройте http://localhost:8080 и войдите, например, `james` / `demo1234` ([все пользователи](#демо-пользователи)). Почта: http://localhost:8025.
4. Пройдите [демо-сценарий](#демо-сценарий-согласования-seeddemo) и [проверку двумя вкладками](#проверка-двумя-вкладками-обновление-без-перезагрузки).

**Порты (только 127.0.0.1):** web 8080, api 3000, Postgres 5432, Mailpit 8025 (интерфейс) и 1025 (SMTP). Порты должны быть свободны.

**Запуск:** `docker compose up` из корня репозитория (`cp .env.example .env` не нужен, демо-значения заданы в `docker-compose.yml`). Страница: http://localhost:8080, проверка API: http://localhost:3000/health, почта: http://localhost:8025. Данные Postgres лежат в именованном томе `pgdata`; полный сброс: `docker compose down -v`.

**Демо-режим** (остановленные часы и полоса для их установки) включён переменной `DEMO_MODE` в `docker-compose.yml` (сервис api, по умолчанию `true`). Чтобы запустить с реальным временем, задайте `DEMO_MODE=false` в файле `.env` рядом с `docker-compose.yml` и перезапустите `docker compose up`: часы станут системными, полосы не будет, маршрут `/clock` ответит 404. Без демо-режима не работают `npm run seed:demo` (сообщит «работает только в демо-режиме»), демо-сценарий этого README и e2e-тесты: им нужно ставить часы. Сохранённое значение демо-часов остаётся в БД и вернётся при `DEMO_MODE=true`.

**Если не запускается:**
- Занят порт: остановите программу, которая его держит, и снова выполните `docker compose up`.
- Windows PowerShell пишет «running scripts is disabled» на `npm`: вызывайте `npm.cmd` вместо `npm` (например, `npm.cmd run seed:demo`) или используйте cmd или Git Bash. Для `seed:demo` есть вариант без npm: `docker compose exec api node dist/seed-demo.js`.

Запуск тестов — раздел [«Тесты и CI»](#тесты-и-ci). Почта и её настройки, проверка стека `smoke:compose`, миграции вне Docker — [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md).

## Как проверить

### Демо-сценарий согласования (seed:demo)

Демо-часы остановлены и меняются только полосой часов в шапке (RULES §9). Даты демо-заявок считаются от текущего значения часов: первая начинается с первого понедельника не раньше «сегодня + 14 дней». Поэтому часы выставляются **до** `seed:demo` (RULES §9-6).

1. `docker compose up` (демо-режим `DEMO_MODE` в compose уже включён).
2. Откройте http://localhost:8080 и войдите любым демо-пользователем, например `james`.
3. В полосе демо-часов укажите дату **21.10.2026** и время **09:00** и нажмите «Установить демо-время».
4. Выполните `npm run seed:demo` (или `docker compose exec api node dist/seed-demo.js`). Повторный запуск ничего не дублирует. Если вкладки приложения уже открыты, после команды перезагрузите их: события `seed:demo` в открытые вкладки не приходят.
5. Что увидеть на странице «Согласование» (даты при часах 21.10.2026):
   - `daniel`: заявка Sophie Bennett 11.11–17.11 с предупреждением о пересечении с одобренным отпуском James Walker 09.11–13.11;
   - `olivia`: заявка Grace Morgan 16.11–20.11 без предупреждения;
   - `emily` (HR): в «Мои заявки» своя заявка 16.11–20.11 «На согласовании», в «Допуск HR» заявка директора Margaret Collins 09.11–13.11;
   - `thomas`: заявка Emily Carter 16.11–20.11;
   - Mailpit (http://localhost:8025): 10 писем — 7 о новых заявках и 3 о решениях.
6. Что увидеть на странице «Календарь» (часы в октябре, поэтому нажмите «Следующий месяц →»; в календаре только одобренные отпуска):
   - `james`: свой отпуск 09.11–13.11;
   - `daniel`: отпуск James Walker 09.11–13.11 и «Остатки команды» (James, Liam, Sophie);
   - `olivia`: отпуск Henry Price 23.11–27.11 (заявка Grace «На согласовании» и отклонённая заявка Chloe не видны);
   - `emily` (HR): вся компания — James Walker и Henry Price.

**Сотрудник 3 (`liam`, выход 12.10.2026).** При часах 21.10.2026 у него ещё нет начислений: на странице «Мой отпуск» заявка не проходит с причиной «У вас ещё нет накопленных дней», а «Доступно на дату» 01.11.2026 показывает первое начисление 1,5 дня (RULES §2, §7). Этот случай виден только при часах до 01.11.2026: позже начисление уже пришло.

**Как переключать дату.** Полосой демо-часов, в любую сторону, любым вошедшим пользователем; после «Установить демо-время» перезагружаются эта и все другие открытые вкладки вошедших пользователей. Откат часов назад не отменяет уже состоявшиеся события (списания, письма), а прогноз «Доступно на дату» может разойтись с фактическим балансом — известное ограничение демо-режима (RULES §9-5). После установки часов подождите 2–3 секунды, прежде чем менять их снова: напоминание, которое диспетчер почты не успел отправить до наступления даты начала отпуска, не отправляется (RULES §8-4; DECISIONS 2026-10-30 14:24).

**Вернуться к началу.** Кнопки «Вернуть реальное время» нет (RULES §11). Сброс часов и данных: `docker compose down -v`, затем `docker compose up` — БД, часы и письма создаются заново. `npm run e2e:reset` и сами e2e-тесты тоже стирают данные и ставят часы: не запускайте их на стеке, где проверяете сценарий вручную.

### Проверка двумя вкладками (обновление без перезагрузки)

Токен хранится в `sessionStorage`, поэтому у каждой вкладки свой вход (RULES §7-4). Откройте две вкладки (или два окна) http://localhost:8080 и войдите разными пользователями, например `daniel` и `emily`, на обеих откройте «Календарь» нужного месяца.

Само, без перезагрузки, обновляется:
- «Календарь» (оба блока и «Остатки команды») и «Экран HR» («Все заявки», «Остатки по сотрудникам») — после одобрения заявки, отмены или отзыва одобренного отпуска, утверждения переноса и смены даты выхода (RULES §10-2). Изменение видят только те, кому отпуск виден по RULES §7-2: например, отпуск James видят daniel и emily, olivia — нет. Смену даты выхода видят сам сотрудник, его руководитель и HR.
- Демо-часы: после «Установить демо-время» в одной вкладке перезагружаются все открытые вкладки вошедших пользователей; несохранённый ввод в формах других вкладок теряется.

После перехода между разделами или перезагрузки обновляется: «Мои заявки» и остаток на странице «Мой отпуск», «Согласование», а в «Все заявки» — подача, отклонение, отмена заявки «На согласовании», подача и отмена переноса (RULES §11; о новой заявке и решении сообщает письмо).

Третьей вкладкой можно открыть коллегу: `sophie` увидит одобренный отпуск `james` в календаре команды без перезагрузки, `olivia` из другой команды — нет.

Если связь с сервером прервалась, вкладка переподключается сама (пауза от 1 до 30 с) и перечитывает данные полностью.

## Как устроено и почему такой стек

**Клиент-сервер.** Backend и frontend — отдельные приложения в отдельных контейнерах, общаются по HTTP:

```
браузер (React SPA) ──HTTP──▶ nginx :8080 ──/api, /events──▶ api (NestJS) :3000 ──▶ PostgreSQL :5432
                                                                   └──SMTP──▶ Mailpit :1025 (письма видны на :8025)
```

REST для чтения и действий, SSE (`GET /events`) для обновления экранов без перезагрузки. Контракт API (OpenAPI), модель данных и модули описаны в [architecture.md](architecture.md).

**Вход.** Логин и пароль (пароли хранятся хешем bcrypt). После входа выдаётся JWT на 8 часов, без refresh-токена: по истечении — «Сессия истекла, войдите снова». Токен хранится в `sessionStorage`, поэтому у каждой вкладки свой пользователь (так проверяются две вкладки). После 5 неудачных попыток по одному логину за 15 минут вход по нему закрыт на 15 минут (RULES §7-1). Все маршруты закрыты по умолчанию, открыты только `/auth/login`, `/config`, `/health`. Роль руководителя (есть подчинённые) и видимость данных вычисляются по структуре подчинения на каждый запрос; HR — признак в данных пользователя.

Языки и библиотеки в задании оставлены на усмотрение автора. Выбор делался под два требования задания: быстрый локальный запуск одной командой и доказуемость поведения тестами. Полный журнал решений: [docs/DECISIONS.md](docs/DECISIONS.md), обоснование по модулям: [architecture.md](architecture.md) (раздел 12).

**Основа**

| Что | Зачем | Почему |
|---|---|---|
| Node.js 24 + TypeScript | backend (`apps/api`) | Один язык на backend и frontend. Node 24 поддерживают NestJS и Prisma 7; в образах, CI и `engines` одна мажорная версия. |
| NestJS 11 (на Express) | каркас API | Модули и внедрение зависимостей ложатся на модульную структуру проекта. Глобальный guard закрывает все маршруты, кроме явно открытых; роли и видимость данных считаются на каждый запрос одной функцией `visibleTo`; один фильтр ошибок даёт единый формат ответов. Минус — больше шаблонного кода, чем в голом Express. |
| PostgreSQL 17 | хранилище | Правила предметной области держит сама БД: `EXCLUDE USING gist` не даёт пересекаться одобренным отпускам, частичные уникальные индексы, `SELECT … FOR UPDATE SKIP LOCKED` для очереди писем. |
| Prisma 7 | ORM и миграции | Типизированная схема и генерируемый клиент. То, что Prisma не выражает (EXCLUDE, триггер возврата, CHECK), лежит в SQL миграции, а расхождение схемы и миграции ловит CI. Взята стабильная 7.x: тег `latest` указывал на 8.0.0-rc. |
| React 19 + Vite | frontend (`apps/web`) | Требование задания (Vue или React). Одностраничное приложение: вход по токену, обновление экранов по SSE. |
| nginx | раздача web | Проксирует `/api`, поэтому CORS не нужен. Защитные заголовки и CSP задаются в одном месте. |
| SSE (`GET /events`) | обновление без перезагрузки | Проще WebSocket, а календарю и экрану HR достаточно односторонних событий. Написан своими средствами. |
| Mailpit + nodemailer | почта | Заглушка внешнего сервиса: принимает SMTP и показывает письма на `localhost:8025`. Транспорт сейчас без авторизации и TLS: для настоящего SMTP-сервера их нужно добавить. |
| Docker Compose | запуск | `docker compose up` поднимает Postgres, Mailpit, api и web. Образы закреплены по версиям. |

**Вспомогательные библиотеки**

- `@nestjs/jwt` и `bcryptjs`: вход по логину и паролю. bcryptjs написан на чистом JS, нативной сборки нет.
- `class-validator` и `class-transformer`: без них `ValidationPipe` в NestJS не работает.
- React Router: маршрутизация и защита страниц по роли.

## Тесты и CI

Команды запускаются из корня репозитория (нужен Node.js 24 и `npm ci`). В Windows PowerShell — `npm.cmd` вместо `npm` (см. выше).

| Команда | Что проверяет | Что должно быть запущено |
|---|---|---|
| `npm test` | unit-тесты api (Jest, в том числе доменная логика) и web (Vitest) | ничего |
| `npm run test:tz` | те же unit-тесты в поясе `America/New_York` (ловят ошибки дат и летнего времени, которых в Бишкеке нет) | ничего |
| `npm run test:int` | integration-тесты api на настоящем Postgres, отдельная БД `leave_test` | `docker compose up -d postgres` |
| `npm run e2e` | Playwright: все сценарии, включая 8 пунктов «Ожидаемого поведения» | весь стек `docker compose up -d --wait`; один раз `npx playwright install chromium`. **Стирает данные стека** перед каждым тестом |
| `npm run lint` | ESLint (в том числе запрет `new Date()` вне модуля часов), Prettier | ничего |
| `npm run typecheck` | TypeScript в api, web, e2e | ничего |
| `npm run trace-rules` | таблица «пункт RULES → тесты»; падает на ссылке на несуществующий пункт | ничего |
| `npm run test:scripts` | тесты служебных скриптов и проверка ссылок: все относительные ссылки и якоря README, docs/PROGRESS.md, docs/DEVELOPMENT.md и docs/sessions/INDEX.md существуют | ничего |
| `npm run smoke:compose` | запуск стека, healthcheck, перезапуск api, том Postgres | Docker; останавливает стек в конце |
| `npm run scan:secrets` | gitleaks по истории git и по рабочему дереву, включая неотслеживаемые файлы | Docker |

Выборочный запуск integration-тестов, другая тестовая БД и `e2e:reset` — [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md).

**CI (GitHub Actions, [.github/workflows/ci.yml](.github/workflows/ci.yml))** на каждый push и PR: lint, typecheck, unit и integration в двух поясах (по умолчанию и `America/New_York`), проверка, что миграция не расходится со схемой Prisma, `test:scripts` и `trace-rules`, `npm audit --audit-level=high`, gitleaks, e2e на поднятом стеке, `fresh-clone` (чистый клон поднимается командами README и проходит демо-сценарий через API).

**Даты и время.** Начисления 1-го числа, напоминания в 09:00, отмена после начала отпуска и обрезка на 1 января зависят от «сегодня». Чтобы не ждать реальных дат, «сегодня» берётся только из подменяемых часов (Clock; прямой `new Date()` запрещён правилом ESLint). В unit- и integration-тестах часы подставляются в коде, в e2e и при ручной проверке — установкой демо-часов: e2e вызывают тот же `PUT /clock`, что кнопка «Установить демо-время» (RULES §9-6).

**Прослеживаемость.** Каждый тест помечен пунктом RULES (`// RULES §3-9`), `npm run trace-rules` печатает таблицу «пункт → тесты». Проведено три слепых аудита (отдельная сессия без истории и документов проекта, только код, тесты, RULES и задание): `docs/audit/audit-1-report.md`, `audit-2-report.md`, `audit-3-report.md`; находки закрыты тестами или записаны в известные ограничения.

**Чего тесты не доказывают:**
- `trace-rules` проверяет ссылку на пункт `§N-k`, но не сверяет тест с каждой фразой пункта.
- e2e идёт только в одном поясе и только в демо-режиме; режим без демо-часов проверен unit- и integration-тестами.
- `fresh-clone` проверяет сценарий README через API на Linux; вход формой, полоса часов, «Календарь» и клон на Windows проверены вручную один раз.
- «Уведомлений в интерфейсе нет» (RULES §8-1) тестом не доказать; получатели писем проверены точными списками по каждому событию.
- gitleaks не проверяет коммиты слияния; `npm audit` в CI ловит только high и выше (34 уязвимости low/moderate в dev-зависимостях исправляются только мажорными версиями).

## Состояние проекта

Все этапы дорожной карты ([docs/ROADMAP.md](docs/ROADMAP.md)) S0–S10 завершены: от правил и архитектуры до оформления интерфейса и этого README. Журнал этапов со ссылками на issue и PR: [docs/PROGRESS.md](docs/PROGRESS.md). Полный список ограничений: issue [#2 «Известные ограничения»](https://github.com/mirlanbeck/leave-management-system/issues/2).

### Работает

- **Запуск:** `docker compose up` поднимает Postgres, Mailpit, api и web с healthcheck; миграции и seed 11 пользователей при старте api; проверено на чистом клоне (Windows вручную, Linux в CI).
- **Вход и роли:** логин и пароль, JWT, лимит попыток; роли и видимость данных по структуре подчинения (RULES §7).
- **Профиль:** имя, дата выхода, команда, руководитель (только чтение).
- **Остаток и накопление:** «Доступно сегодня» и «Доступно на дату», начисления 1-го числа, первое начисление пропорционально, обрезка до 15 дней на 1 января (RULES §2, §3).
- **Заявка:** все проверки формы и остатка с объяснением причины, заявки «в прошлом» с комментарием; двойной клик даёт одну заявку и одно письмо (RULES §3, §10).
- **Согласование:** подтверждение или отклонение с комментарием, повторная проверка остатка, предупреждение о пересечениях в команде, «допуск HR» для директора, «уже обработана» при решении из второй вкладки (RULES §4).
- **Отмена, отзыв, перенос:** отмена до начала с полным возвратом, отзыв HR из идущего отпуска с возвратом неиспользованных дней, перенос с цепочками A→B→C (RULES §5).
- **Дата выхода:** HR меняет в любую сторону, начисления пересчитываются, остаток может стать отрицательным со знаком минус (RULES §6).
- **Письма:** о новой заявке, о решении, напоминание за `REMINDER_DAYS` рабочих дней в 09:00, по одному на получателя, в том числе при двойном клике, перезапуске и откате часов (RULES §8).
- **Календарь и экран HR:** только одобренные отпуска по видимости, обновление без перезагрузки по SSE (RULES §7-2, §10-2).
- **Демо-часы:** полоса в шапке, смена даты в обе стороны, перезагрузка всех вкладок (RULES §9).
- **Защита:** защитные заголовки и CSP, CORS не нужен, порты только на 127.0.0.1, без `DEMO_MODE` маршрута часов нет; сканирование секретов и `npm audit` в CI.
- **Интерфейс:** вёрстка до ширины 375 px (на телефоне таблицы становятся карточками), «сегодня» отмечено в календаре.

### Не работает (известные ограничения)

Поведение, на которое можно наткнуться при проверке:

- **Нет refresh-токена:** через 8 часов нужно войти снова. Токен лежит в `sessionStorage` и доступен скрипту страницы при XSS; CSP без `'unsafe-inline'` снижает этот риск, но не убирает (DECISIONS 2026-10-22 12:15).
- **«Доступно на дату D» консервативно:** прогноз вычитает все одобренные списания, даже по отпускам позже D. Пример: отпуск на 20 дней с 15 января одобрен, сегодня 1 декабря — «доступно на 1 января» покажет остаток уже без этих 20 дней. Заявка на более ранние даты может быть отклонена, хотя по-человечески дни на неё есть (RULES §3-10; DECISIONS 2026-10-20, 2026-10-21 11:03).
- **Остаток одним числом:** после одобрения отпуска в счёт будущих начислений он уходит в минус до следующих начислений (RULES §6-4).
- **Откат демо-часов** не пересчитывает и не отменяет списания и письма; прогноз может разойтись с фактическим балансом (RULES §9-5).
- **Дата выхода после согласования:** если HR сдвинул дату выхода на более позднюю, согласование и перенос не проверяют «начало не раньше даты выхода»; свою дату выхода HR меняет без отдельного контроля (DECISIONS 2026-10-28 19:19, 2026-10-24 10:52).
- **Отмена переноса, когда старый отпуск уже начался,** отдельно не проработана: действует общее правило отмены по дате начала самого переноса; утвердить такой перенос нельзя, только отклонить (RULES §5; ROADMAP, вопрос N4).
- **Отозванный отпуск** пропадает из календаря целиком, хотя использованные дни списаны (RULES §5-5).
- **Свой отпуск HR отзывает сам** (RULES §5-5).
- **Без перезагрузки обновляются только «Календарь» и «Экран HR»** (события RULES §10-2). «Мои заявки», остаток на «Моём отпуске», «Согласование» и часть событий «Всех заявок» — после перехода или перезагрузки (RULES §11).
- **События при обрыве связи теряются:** после переподключения вкладка перечитывает данные полностью (DECISIONS 2026-10-29 21:41).
- **Не больше 6 вкладок** приложения в одном браузере: седьмая ждёт (ограничение HTTP/1.1, DECISIONS 2026-10-29 22:26).
- **Дубль письма** возможен, если api упадёт между ответом SMTP и пометкой «отправлено».
- **Письмо о новой заявке** может прийти руководителю после её отмены, если отмена случилась до отправки письма (обычно это окно около 2 секунд, при недоступной почте — до её восстановления) (DECISIONS 2026-10-26 14:14).
- **Лимит попыток входа хранится в памяти api:** перезапуск снимает блокировки; зная логин, можно на 15 минут закрыть вход другому пользователю (RULES §7-1).
- **Ошибка лишнего поля** в теле запроса приходит стандартным английским текстом class-validator, остальные сообщения — по-русски.
- **Название команды** пустое у директора, заместителя, HR и руководителей (RULES §7; ROADMAP N6 a).

Особенности запуска (занятые порты, `npm.cmd` в PowerShell) описаны в [«Требованиях к окружению»](#требования-к-окружению), `e2e:reset` — в [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md), пределы тестов — в [«Тесты и CI»](#тесты-и-ci). Технические ограничения, недостижимые из интерфейса и API, — в issue [#2](https://github.com/mirlanbeck/leave-management-system/issues/2).

### Не делали и почему

Объём ограничен тем, что требует задание; всё остальное записано в [RULES §11](docs/RULES.md#11-список-следующим-заходом-не-в-объёме-работы) с самого начала, чтобы не расширять задачу по ходу.

| Что не делали | Почему |
|---|---|
| Праздничные дни, часовой пояс у каждого сотрудника | Задание этого не требует; один пояс и рабочие дни пн–пт упрощают все расчёты (RULES §1; DECISIONS 2026-10-20) |
| Письма backstopper и письма HR об отменах и переносах | Задание требует письма руководителю о заявке и сотруднику о решении; остальные изменения видны в календаре (RULES §8; DECISIONS 2026-10-20) |
| Управление составом команд из интерфейса | Структура задаётся демо-данными, в задании управления нет (DECISIONS 2026-10-21 09:42) |
| Кнопка «Вернуть реальное время» | Для проверки достаточно переставлять часы и сбрасывать стек (`docker compose down -v`) (RULES §9) |
| Решение и комментарий согласующего в «Моих заявках» | В задании сотрудник узнаёт о решении уведомлением — письмо это делает (DECISIONS 2026-10-28 11:29) |
| Отзыв HR из своего отпуска заместителем директора | Иначе начавшийся отпуск HR не сокращает никто; передача права — отдельная роль (DECISIONS 2026-10-28 15:41) |
| Использованная часть отозванного отпуска в календаре | Найдено аудитом 2 (F-3), правило статуса после отзыва выбрано простым (DECISIONS 2026-10-29 06:15) |
| «Все заявки» без перезагрузки по всем событиям | Задание требует обновления календаря; раздел обновляется по тем же событиям (DECISIONS 2026-10-29 22:26) |

### Что не вошло в объём и стоит сделать

**Новые возможности**
- Больничные: отметка больничного с датами, отпускные дни не тратятся. Открытый вопрос: если больничный пришёлся на одобренный отпуск — продлевать отпуск или возвращать дни.
- Командировки: заявка с местом, целью, планом и датами, согласование руководителем, отдельный цвет в календаре команды, отпускные дни не тратятся. Открытый вопрос: пересечение с отпуском запрещать или только предупреждать.
- Решение и комментарий согласующего в «Моих заявках».
- Управление составом команд и назначение руководителя из интерфейса HR.
- Праздничные дни в расчёте рабочих дней; часовой пояс у каждого сотрудника.
- Письма backstopper и письма HR об отменах и переносах.
- Кнопка «Вернуть реальное время» в демо-режиме.
- Показ использованной части отозванного отпуска; запрет даты выхода при отзыве на выходной.
- Остаток двумя числами: «накоплено на сегодня» и «занято одобренными отпусками».
- Отзыв HR из своего отпуска заместителем директора.

**Точность правил**
- «Доступно на дату D» с учётом только списаний, которые наступят к D.
- Решение для отмены переноса, когда старый отпуск уже начался (N4).
- Проверка «начало не раньше даты выхода» при согласовании и переносе после сдвига даты выхода; контроль смены даты выхода HR самой себе.

**Надёжность и безопасность**
- Refresh-токен и cookie `httpOnly` вместо `sessionStorage`.
- Доставка пропущенных событий после переподключения вместо полного перечитывания; обновление без перезагрузки на всех экранах.
- Письма без дублей при сбое между SMTP и пометкой «отправлено».
- Счётчик попыток входа в БД, чтобы блокировка переживала перезапуск.
- Русский текст ошибки лишнего поля.

**Проверка**
- Сверка теста с каждой фразой пункта RULES, а не только с номером пункта.
- e2e в другом часовом поясе и без демо-режима.
- Перенаправление неотправленного напоминания при смене руководителя (если смена появится).

## Видение формулировок требований

Как понимаются неоднозначные места задания. Каждый пункт подтверждается, когда соответствующая часть работает.

- **Календарь** (подтверждено, S5-e, S6-audit): на странице два блока — «Мои отпуска» сверху и календарь команды снизу. Сотрудник видит в нём одобренные отпуска коллег с тем же руководителем и самого руководителя (но не их заявки и остатки), руководитель — прямых подчинённых, HR — всю компанию (RULES §7-2; DECISIONS 2026-10-29 09:01).
- **Отмена начавшегося отпуска** (подтверждено, S6-a): сотрудник сам отменить не может, это делает HR отзывом с датой выхода; возвращаются неиспользованные рабочие дни (RULES §5; DECISIONS 2026-10-22 12:15). Неиспользованные считаются с фактической даты выхода: HR может указать её задним числом (дата выхода раньше сегодня), и дни с неё возвращаются (RULES §5-11; DECISIONS 2026-10-22 15:35, 2026-10-29).
- **«Подтвердить или отклонить с комментарием»:** комментарий согласующего возможен, но необязателен (RULES §4-1; DECISIONS 2026-10-21 09:31).
- **«За заданное число дней» до начала отпуска:** число рабочих дней, `REMINDER_DAYS`, по умолчанию 3: вся арифметика отпусков идёт в рабочих днях, и письмо не приходит в выходной (RULES §8-3; DECISIONS 2026-10-20 22:36).
- **«Изменение даты выхода на работу пересчитывает накопление»:** дата выхода — это дата начала работы из профиля; её меняет HR, начисления пересчитываются (RULES §6). Если имелся в виду ранний выход из отпуска, это отзыв HR с датой выхода: неиспользованные дни возвращаются (RULES §5; DECISIONS 2026-10-30 14:24).
- **«Работает при двух одновременно открытых клиентах»:** оба клиента работают одновременно, повторное решение по уже обработанной заявке отклоняется (RULES §10-1); календарь и экран HR обновляются без перезагрузки, остальные экраны — после перехода (RULES §10-2, §11).
- **Отрицательный остаток:** заявка проходит, если дней хватит к дате начала отпуска, а списывается сразу целиком, поэтому после одобрения отпуска в счёт будущих начислений «Доступно сегодня» может быть с минусом; так же после сдвига даты выхода и отката демо-часов (RULES §6-4; DECISIONS 2026-10-30 14:24).
- **«Если в команде уже есть согласованный отпуск»:** команда — прямые подчинённые согласующего и он сам; для заявки руководителя это другие прямые подчинённые его начальника и сам начальник, для директора (допуск HR) — прямые подчинённые директора и сам директор (RULES §4-6).
- **«Заявка на больше дней, чем будет накоплено, не проходит»:** относится к новой заявке; у переноса остаток не проверяется, число рабочих дней то же, списание остаётся прежним (RULES §5-2; DECISIONS 2026-10-21 16:10).
- **«Правила дробления»:** дробление свободное — любая часть от 1 рабочего дня, число частей не ограничено; проверяются год, минимум 1 рабочий день и пересечения. Содержательное ограничение вроде «одна часть не короче 14 дней» не выбрано (RULES §3; DECISIONS 2026-10-20 22:36).

## Как делали

- **Инструмент:** Claude Code (расширение для VS Code). Работает прямо в репозитории: читает код, правит файлы, запускает команды и тесты, а каждая сессия сохраняется в JSONL-журнал с временными метками.
- **Модели:** Claude Sonnet 5.5 на первых этапах (20.10–26.10: правила, S0–S3), затем Claude Opus 5.5 до конца работы — около 73% всех ответов агента. Уровень рассуждений — medium на всём протяжении. Сначала выбор был в пользу Sonnet как более экономной модели. Когда стало ясно, что работа спокойно укладывается в лимиты тарифа, основной стала Opus: более сильная модель для длинных рассуждений над правилами, аудитов и сверки кода с RULES. Доли посчитаны по журналам сессий (поле модели в ответах агента).
- **Вне Claude Code:** отдельные вопросы (разбор требований, расход лимитов, формулировки для документации) обсуждались в чате claude.ai. Код проекта этим чатом не писался.
- **Как шла работа:** сначала правила ([docs/RULES.md](docs/RULES.md)) и дорожная карта ([docs/ROADMAP.md](docs/ROADMAP.md)), потом этапы S0–S10. На каждый этап — issue с критериями приёмки, план агента, утверждение автором, ветка, PR. Агент не меняет правила сам: расхождение кода с RULES он сообщает, а решение записывается в DECISIONS. Три слепых аудита проводились отдельной сессией без истории и документов проекта.
- **Лог решений и промпты:** [docs/DECISIONS.md](docs/DECISIONS.md) — решения с датой, временем и пунктом RULES; [docs/AI-LOG.md](docs/AI-LOG.md) — ключевые промпты и что автор исправил вручную; история коммитов и PR.
- **Сессии агента:** стенограммы всех рабочих сессий Claude Code — [docs/sessions/INDEX.md](docs/sessions/INDEX.md) (список и с чего начать). Они получены скриптом из журналов JSONL: промпты и ответы агента полностью, действия агента одной строкой; пути, email и токены заменены заглушками. **Почему стенограммы, а не JSONL:** исходные журналы — 78 файлов, около 200 МБ, и почти весь их объём — вывод инструментов (содержимое прочитанных файлов, логи тестов и сборки) и служебные записи. Стенограммы (около 4,5 МБ) сохраняют сам диалог с агентом, читаются прямо на GitHub и проверены на секреты и личные данные. Скрипт: [scripts/session-transcripts.mjs](scripts/session-transcripts.mjs).
- **Чужие решения, шаблоны, генераторы:** не использовались. Проект не создавался через `nest new`, `prisma init` или шаблон Vite: файлы написаны в сессиях с агентом с нуля. Готовыми взяты только npm-библиотеки (раздел «Стек») и Docker-образы `node`, `nginx`, `postgres`, `axllent/mailpit`.
